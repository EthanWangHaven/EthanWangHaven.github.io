上一篇末尾留了一条判据：KV 读取占比过了 65%（长上下文加大 batch）之后，它才是每步访存的主导项，这时候才轮到 KV cache 的压缩出场。这篇把围绕这件事的 8 篇论文过一遍。

读这批最大的收获是：五条路线省的东西完全不是一回事——省浪费、省内容、按头省、省位宽、省位置。它们可以叠用，但数字口径完全不可互换，这也是我这批笔记里返工最多的地方。

## PagedAttention：省的不是 KV，是浪费

严格说 PagedAttention（SOSP '23）不是压缩方法，它省的是浪费。现有系统给每个请求按最大可能长度预分配一段连续显存，实测只有 20.4%~38.2% 的 KV 显存真正存了 token 状态，其余全是内部碎片（预分配 2048、实用 300）、外部碎片和预留。做法是把 KV 切成固定大小的块、非连续存放、按需分配，块表类比操作系统的页表；再往上加引用计数和写时复制，让并行采样、beam search 这类"一个 prompt 派生多条序列"的场景共享 KV。

结果：吞吐比 SOTA 高 2~4 倍，延迟相当。两个容易误读的地方：2~4× 是吞吐不是单请求延迟，论文自己写明延迟相当；它现在根本不是"可选优化"——vLLM 的默认行为就是它，做对比实验时它已经在 baseline 里，不能再单独计一次收益。另外作者自陈注意力核因此多了 20~26% 的额外延迟开销，这是引入分页的代价，不该算进净收益。

## 驱逐这条路：H2O 起头，SnapKV 补漏，Ada-KV 再补

驱逐 / 稀疏这条线的演进链是全部笔记里最清楚的一条，值得按顺序读。

H2O（NeurIPS 2023）的立足点是两个观察：预训练模型的注意力矩阵推理时 95% 以上稀疏；token 的累积注意力分数服从幂律分布，少数"重击者"贡献了大部分注意力值，删掉它们精度骤降。策略于是定为只保留重击者加最近窗口，每步按累积分数贪心淘汰最低分者，还配了一个 dynamic submodular 的理论界。20% 的预算做到 5× KV 压缩、精度持平。

H2O 有两个后来被戳的漏洞。其一，它只压 decode 新增的 KV，不压 prompt 侧——而长 prompt 场景下 prompt 的 KV 才是大头。其二，它必须先算出完整的注意力矩阵再淘汰，这本身就有时间和显存代价。

SnapKV（2024）把这两个漏洞一起补了。核心观察：各注意力头对 prompt 的关注模式，在生成开始前就能由 prompt 末端的观察窗口识别出来，并且在生成过程中保持一致。于是不等 decode，直接在 prompt 末端窗口内做投票选 Top-k，再 1D pooling 保住邻域——不然纯 Top-k 会把上下文切碎，论文自己的比喻是"只留了区号、丢了号码"。全程 test-time，免微调。16K 输入下生成加速 3.6×，LongBench 上容量 1024 时压缩 92%、4096 时 68%，精度几乎无损。要注意压缩率和精度是同一根旋钮的两端：1024 容量换 92% 压缩，4096 换 68%，预算选错直接体现在精度上。

Ada-KV（NeurIPS 2025）再补一刀，这次砍的是 H2O 和 SnapKV 共同的隐含假设：给每个头分配相同的 KV 预算。实际上各头的注意力集中度差异极大，多数头 top-5% 就覆盖了几乎全部注意力权重。Ada-KV 把一层内所有头的注意力权重拼起来做一次全局 Top-k，再按各头入选的个数直接定预算——不做额外排序，所以效率与均匀分配持平，收益全在精度侧（80% / 20% 预算下把 SnapKV 的分数从 87.59 / 44.02 提到 92.67 / 53.29）。它是插件式的，价值在精度不在速度。

这条线里最需要警惕的数字是 H2O 的 29×。它特别容易被误读成"对注意力实现的加速"，实际基线是 DeepSpeed ZeRO-Inference 和 HF Accelerate 两个 CPU offload 方案——本身就慢得多；对同类系统 FlexGen 只有 3×。同属这条线的 Scissorhands 整篇没有 wall-clock 数字（它靠"重要性持续性"假设做固定预算管理，KV 压缩 5×），只能引压缩比，不能引加速比。还有个有意思的自我反例：作者拿随机初始化的 OPT 做对照，发现重复注意力模式消失了——重要性持续是训练的产物，不是架构的保证。

## DuoAttention：把头分成两类

驱逐方法都在 token 维度动刀、对所有头一视同仁。DuoAttention 换了个维度：注意力头本身分两类——少数 retrieval 头对全部 token 需要完整注意力，多数 streaming 头只看 attention sink 加最近窗口就够了。于是少数头保全量 KV，多数头只留常数窗口，内存不随序列涨。

两个设计上的好处值得记：streaming 头不依赖 decode 阶段的注意力分数，所以能同时加速 prefill，这是 token 驱逐法做不到的；实现上它离线重排 Q/K/V 输出通道、把两类头排成连续块，不改 attention kernel，所以兼容 FlashAttention-2、GQA 和量化。

数字：KV 显存 2.55×（MHA）/ 1.67×（GQA），decode 提速 2.18× / 1.50×，prefill 也提速 1.73× / 1.63×。

实操层面它对我是八篇里最友好的：官方仓库直接发布了 6 个 7B / 8B 模型的预计算 pattern，原本要 8×A100 跑数小时的标定可以整个跳过。坑也明确：Mistral-7B-v0.3 的 pattern 文件是错的（只有 32 层，模型实际 36 层，issue #23），别用那一个；transformers 必须锁 4.45.2。另外标定出的 gate 值是模型权重的属性、跟 GPU 无关，所以在别的卡上标定的结果可以直接搬到 A800 / 4090 用。

短板：短上下文几乎无收益（streaming 头还是要保留约 80 个 sink + recent token），retrieval 头的计算和显存一点没省，只是被比例缩放。

## KIVI：key 和 value 得分开对待

KIVI（ICML 2024）处理的是位宽。它开篇先讲清楚 KV 量化和权重量化的根本差别：权重可以离线慢慢优化（像 GPTQ 那样用二阶信息），KV 是流式的，每步生成即新增，必须立刻量化，只能退化成 round-to-nearest。而在这个约束下 per-tensor 全量化会死在离群值上——key 的少数固定通道幅值极大，统一的 scale 被拉爆，正常通道被压扁。

所以它的核心是一个不对称设计：key 按 channel 分组量化（组 32），把离群值关进各自的组；value 没有离群模式，按 token 量化，借注意力稀疏性把误差锁在单个 token 里。为了兼容流式，KV 拆成"每 32 个 token 一组的量化存储 + 最近 128 个 token 的全精度滑窗"两部分——per-channel 量化跨 token 没法流式，这一拆就是解法。

数字：key 分组后注意力相对误差 47.0 降到 9.6（约 5 倍）；2bit 在 Llama-2-7B 的 CoQA 上 63.05 对 63.88；峰值显存降 2.6×——注意这个数含权重，单看 KV 的降幅比它大；吞吐 2.35~3.47×。

失效条件写得也很实在：Falcon-7B 这种 MQA 结构 2bit 直接掉大分，得退到 4bit；GSM8K 这类难推理任务去掉全精度滑窗就崩。这条对我直接相关——Qwen2.5-7B 是 GQA，2bit 行不行得先自己验证，不能默认 KIVI 的结论直接适用。

## ShadowKV：把 value 搬去 CPU

ShadowKV 的分工建立在一个结构性发现上：pre-RoPE 的 key 是极低秩的，只存低秩投影（rank 160）就够了；value 不是低秩的，干脆卸载到 CPU，用时在线重建。卸载取数慢，用多流重叠把 value 的 PCIe 传输和 key 的低秩重建藏起来；另存 0.2%~0.3% 的难近似 outlier 块做 GPU 上的高精度缓存补精度。三个机制是一条链：key 低秩省显存、value 卸载省显存、少量 outlier 补精度。

数字：KV 显存理论上限 7.08×，实测 6× 压缩不掉精度；吞吐最高 3.04×。两个口径要分清：常被引的"等效带宽 7.2 TB/s = 3.6× A100"是等效口径，不是端到端吞吐。前提也得带上：CPU 内存必须装得下完整的 value cache，长序列大 batch 时是几十 GB——显存压力没有消失，只是从 GPU 挪到了主机。论文没有独立的 Limitations 章节，这几点是我从正文里抠出来的。

## 八篇放一张表

| 论文 | 省什么 | 压缩 / 显存 | 吞吐或速度 | 精度 |
|---|---|---|---|---|
| PagedAttention | 浪费 | 利用率 20~38% → 近 100% | 吞吐 2~4× | 无损失 |
| H2O | 内容 | KV 5× | 吞吐至多 29×（对 CPU offload 基线） | 20% 预算持平 |
| SnapKV | 内容 | 92%（1024）/ 68%（4096） | 生成加速 3.6×，内存效率 8.2× | 几乎无损 |
| Scissorhands | 内容 | 最多 5× | 未给 wall-clock | 15~30% 保留仍保持 |
| DuoAttention | 按头 | 2.55× / 1.67× | decode 2.18× / 1.50× | 近无损 |
| KIVI | 位宽 | 显存 2.6×（含权重） | 吞吐 2.35~3.47× | 2bit 近无损（除 MQA） |
| ShadowKV | 位置 | 6×（上限 7.08×） | 吞吐 3.04× | 不掉 |
| Ada-KV | 内容 + 预算 | 同预算下更好 | 与 SnapKV 持平 | 同预算下更高 |

读这张表只要记住一句：压缩比（显存 / 容量）、吞吐、单请求延迟是三个不同的量，不能互换。表里 Scissorhands 是唯一没有任何时间侧数据的，偏偏它的 5× 最常被误读成"加速 5×"。

## 共同的边界：长上下文

除 PagedAttention 外，这批方法的收益全部出现在长上下文。原因从上一篇的实测直接能读出来：短上下文小 batch 时 KV 只占每步访存的 4%~9.5%，就算全压掉，天花板也只有个位数百分比。

所以我自己的实验顺序是：先在 4090 上扫上下文长度，找显存逼近 24GB 的那一档。边界落在 8K 以下就转短上下文、主线换权重量化（下一篇），16K 以上才做 KV 压缩。这个边界我不用公式估——vLLM 的 `gpu_memory_utilization` 预留、KV 分块、prefix caching 让实际占用跟理论值差得不小，估出来的边界会误导后面所有实验设计。
