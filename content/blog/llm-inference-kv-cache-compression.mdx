上一篇确立了一条判据：**decode 每一步都要把整条 KV cache 读一遍**。当 KV 读取占比超过 65% 时（长上下文 + 大 batch），它才是主导项。

这一篇梳理围绕"让 KV cache 变小 / 少读"已经成型的五类解法，共 8 篇论文。五类作用在互不重叠的维度上，可以叠用，但**省的东西完全不同**，混着引用最容易出错。



## 一、五类解法：省的东西不是一回事

| 路线 | 代表 | 省的是什么 | 可逆性 | 是否损精度 |
|---|---|---|---|---|
| 内存管理（分页） | PagedAttention | 省**浪费**（碎片），不减少总量 | — | 不损（多 20~26% 核延迟） |
| 驱逐 / 稀疏 | H2O、SnapKV、Scissorhands、Ada-KV | 省**内容**（丢 token） | **不可逆** | 有损（预算足时近无损） |
| 架构级分类 | DuoAttention | 按**注意力头**分而治之 | 部分可逆（分类静态） | 近无损 |
| 量化 | KIVI | 省**位宽** | 数据都在，只是精度低 | 有损（2bit 时难任务明显） |
| 低秩 + 卸载 | ShadowKV | 省**位置**（搬到 CPU） | 可逆（数据在 CPU） | 不损（有 outlier 补精度） |

一个必须记下的区分：**PagedAttention 不减少 KV 总量**，只让显存别浪费。它和其余四类正交，可以叠用——这也解释了它为什么成了 vLLM 的默认行为。

路线分布很不均匀：驱逐 / 稀疏一路 4 篇，其余各 1 篇。这条线的演进链最清楚，也最能看出方法是怎么迭代的：

```
H2O (2023)      按重要性淘汰 + 理论界
  └→ SnapKV (2024)  指出 H2O 不压 prompt KV、且需完整注意力矩阵
      └→ Ada-KV (2025)  指出 H2O / SnapKV 共同默认的"每头等预算"不成立
```

三条独立观察支撑同一个方向：H2O 测到注意力矩阵推理时 **>95% 稀疏**；Scissorhands 测到关键 token 持续率多数层 **>95%**；SnapKV 测到关注模式在生成前就由 prompt 末端窗口确定。

## 二、分页：PagedAttention（vLLM）

**出处**：SOSP '23，arXiv:2309.06180 | **开源**：vLLM 本体 | **平台**：A100 40GB 单卡 / 8×A100-80GB

**问题**：现有系统给每个请求按**最大可能长度**预分配一段连续显存，于是同时产生三类浪费——内部碎片（预分配 2048、实用 300）、外部碎片（空洞拼不成连续块）、预留（为将来增长先占着）。实测后果是现有系统只有 **20.4%~38.2%** 的 KV cache 显存真正存了 token 状态。

**方法**：

1. 把 KV cache 切成固定大小的 block，非连续存放，按需分配；逻辑块到物理块的映射靠一张块表（类比操作系统的虚拟内存页表）。
2. 在块表之上做**引用计数 + 写时复制**：同一段 prompt 的 KV 块被多个序列引用，谁改谁才复制，从而在并行采样 / beam search 中共享 KV。
3. 落成完整系统：块级 KV 管理器 + 抢占式调度 + 融合 CUDA 核。

**关键数字**：吞吐较 SOTA 提升 **2~4×**，延迟相当；请求承载能力相对 Orca(Oracle) 1.7~2.7×、相对 FasterTransformer 最多 22×；并行采样省显存 6%~55%，beam search 省 37.6%~66.3%。

**代价**：作者自陈 **注意力核本身带来 20~26% 的额外延迟开销**。方法不普适——训练的张量形状静态，非 LLM 任务引入分页反而因间接寻址变慢。

> **口径**：2~4× 是**吞吐**提升，不是单请求延迟下降（论文明确写延迟相当）。22× 是相对 FasterTransformer 的请求承载能力，不是吞吐。

> **现在它已不是"可选优化"**：它是 vLLM 的默认行为。做任何对比实验时它已在 baseline 里，不宜再作为加速手段单独计一次。

## 三、驱逐：丢掉不重要的 token

四篇的共同假设是：注意力集中在少数 token 上，其余可以丢。分歧在于**按什么评分、什么时候评、每头给多少预算**。

### 3.1 H2O：按累积注意力分数淘汰

**出处**：NeurIPS 2023，arXiv:2306.14048 | **开源**：`FMInference/H2O` | **平台**：单卡 A100 80GB

**两个观察**：预训练 LLM 的注意力矩阵推理时 >95% 稀疏；token 的累积注意力分数服从幂律分布——少数 token 贡献了大部分注意力值，删掉它们精度骤降。

**方法**：

1. 评分函数取累积注意力分数：$F_{\text{score}}(T) = \sum_{s \in T} o_s$。
2. 每步只用局部统计做贪心淘汰，丢掉最低分者，同时保留最近窗口 + 重击者（H2）。
3. 建模为 dynamic submodular，为贪心策略提供理论保证：$f(\tilde S) \ge (1-\alpha)(1-1/e)\max f(S) - \beta$。
4. 在 FlexGen 上落地：预分配内存、环形队列、淘汰时直接覆盖。

**关键数字**：20% 的 H2 预算 = **5× KV 压缩**，多数任务持平全量精度。支持最长 4M token。

**代价**：累积分数偏向最早出现的 token（H2 多在句首）；**淘汰不可逆**；只压缩 decode 阶段新增的 KV，**不压 prompt 阶段的 KV**——这一点由 SnapKV 明确指出。

> **口径最关键**：常被引用的 **29× 是相对 DeepSpeed ZeRO-Inference 与 HF Accelerate 这两个 CPU offload 基线**，两者本身很慢；相对同类推理系统 FlexGen 只有 **3×**。引用时必须写清基线，否则 29× 会被读成"对注意力实现的加速"。
>
> 5× 是 **KV 压缩比**，不是吞吐提升，也不是延迟下降（延迟单独报 1.1~1.9×）。

### 3.2 SnapKV：在生成开始前就预判

**出处**：arXiv:2404.14469v2，2024-06 | **开源**：`FasterDecoding/SnapKV`（论文正文未印链接） | **平台**：单卡 A100-80GB

**针对 H2O 的两个缺陷**：① H2O 必须先算并保存完整注意力矩阵，本身有额外代价；② H2O 忽略 prompt 阶段的 KV，而长 prompt 下 prompt 的 KV 才是内存真瓶颈。

**核心观察**：各注意力头对 prompt 的关注模式，在生成开始前就能由 prompt **末端的窗口**识别出来，并在生成过程中保持一致。

**方法**：

1. 在观察窗口（prompt 末 L_obs 段）内，各 query 对全部 prefix key 的注意力沿 query 维求和做**投票**，取 Top-k 选出重要的 prefix 位置。
2. 投票后做 **1D pooling 聚类**，保留选中特征的邻域，避免纯 Top-k 把上下文切碎（只留区号、丢了号码）。
3. 全程是 test-time 的选择与 gather，不动权重，因此免微调。

**关键数字**：16K 输入下生成加速 **3.6×**、内存效率 **8.2×**；LongBench 上容量 1024 时平均压缩 92%、4096 时 68%，精度几乎无损；单卡 A100-80GB 可处理最长 380K token，而基线 33K 就 OOM。

**代价**：仅作用于生成阶段的 KV，不覆盖 prompt 前向；超参（观察窗口 / 池化核 / 容量）需按模型调。压缩率与精度是同一根旋钮的两端：1024 容量对 92% 压缩、4096 对 68%。

> 三个口径分开记：3.6× 是**生成加速**，8.2× 是**内存效率**，92% / 68% 是**压缩率**。三者不是同一件事。

### 3.3 Scissorhands：重要性会持续

**出处**：arXiv:2305.17118v2 | **开源**：**无官方仓库**（社区常引地址实测 404） | **平台**：4×A100 40GB

**理论支点——重要性持续性假设**：只有在一个先前 step 产生过显著影响的关键 token，才会在未来 step 继续产生显著影响。若成立，就能在生成早期预判未来仍重要的 token。

实证支撑是：后半句的关键 token 集合几乎被前半句包含，多数层持续率 >95%，只在靠后的层下降。

**方法**：以固定预算 B 在序列维度管理 KV，缓存大小恒 ≤ B。三条设计原则：① 用注意力分数在历史窗口上的**累计**作为重要性记录；② 历史窗 w=400 降方差，近期窗 r=10 必须保留；③ 按重要性排序丢最低分，每次丢弃 0.5B 个。靠后的层持续率低，故给后层分配更多预算。

**关键数字**：KV cache 最多压缩 **5×**；保留原缓存 15%~30% 时精度仍保持；压缩近似线性转化为 batch size 提升。

**代价**：作者用**随机初始化的 OPT 做对照，发现重复注意力模式消失**——这说明重要性持续是训练产物，不是架构保证。理论只是条件成立（需要注意力分数服从幂律分布），分布不平滑时保证失效。

> **口径红线**：论文没给 wall-clock 数字，只能说"KV cache 压缩 5×"，**不能说"加速 5×"**。它给的换算是"压缩近似线性转化为 batch size 提升"，这是容量侧推论，不是时间侧实测。

### 3.4 Ada-KV：每头预算不该相同

**出处**：NeurIPS 2025，arXiv:2407.11550v5 | **开源**：`FFY0/AdaKV` | **平台**：正文未列 GPU 型号

**问题**：H2O / SnapKV 这类 Top-k 方法有共同假设——**给每个注意力头分配相同的 KV 预算**。这不成立：多数头 top-5% 就覆盖近乎全部注意力权重，少数头分布很分散。均匀分配的结果是稀疏的头浪费预算、分散的头损失较大。

**方法**：

1. 定义 L1 eviction loss，证明其上界 $\varepsilon = 2hC - 2C \sum I \cdot A$；Top-k 最小化 ε，自适应分配达到最小上界。
2. 不做额外排序以控制开销：把一层内所有头的注意力权重拼接，**只做一次全局 Top-k(B)**，再按各头入选个数直接定其预算。加 safeguard 防止小预算。
3. 系统层用扁平化布局 + 自定义 CUDA kernel 支持变长 FlashAttention，兼容 GQA。

**关键数字**：Llama-3.1-8B、question-agnostic、80% / 20% 预算下，Ada-SnapKV 把 SnapKV 的分数从 87.59 / 44.02 提到 **92.67 / 53.29**；难任务 S-NIAH-3、MK-NIAH-2 从 62.4 / 85.2 提到 **97.6 / 99.6**。效率与均匀分配**持平**。

**代价**：head-wise 分配仅限单层内，未跨层；Code 类任务对压缩不敏感，收益集中在 QA 与摘要。

> 这是**插件式**方法：收益是"同预算下比 SnapKV / Pyramid 好"，不是新增一套压缩。它自身的效率与均匀分配持平——**价值在精度而不在速度**。另外正文未列 GPU 型号，效率数字平台不明。

## 四、按头分类：DuoAttention

**出处**：arXiv:2410.10819v1 | **开源**：`mit-han-lab/duo-attention`，**官方已发布预计算 pattern** | **平台**：效率实验单张 A100-80G，标定 8×A100

**核心观察**：注意力头分两类——**retrieval heads**（少数）对全部 token 需要完整注意力；**streaming heads**（多数）只看 attention sink + 最近窗口就够。

与"驱逐 token"的本质区别：H2O / SnapKV 按 **token** 淘汰、对所有头统一处理；DuoAttention **按头分类**，少数头保全量 KV，多数头只留常数窗口。由此两个好处：streaming 头的内存是 **O(1)**、不随序列增长；**不依赖 decode 阶段的注意力分数**，因此能同时加速 prefill——这是 token 淘汰法做不到的。

**方法**：

1. 给每个 KV head 设一个可训练的门 α，前向时混合 full attention 与 streaming attention，在合成 passkey 数据上做蒸馏损失 + L1 正则。**只训 N×H 个标量，模型其余部分冻结**，2000 步 / 8×A100 数小时。
2. 按阈值 τ 二值化门值，**离线重排 Q/K/V 输出通道**，把两类头排成连续块，每层维护两个 KV cache。因此**无需改 attention kernel**，兼容 FlashAttention-2、GQA 与量化。
3. **标定可以完全跳过**：官方仓库 `attn_patterns/` 已发布 6 个模型（Llama-2-7B-32K、Llama-3-8B、Mistral-7B-v0.2/v0.3、Llama-3.1-8B）的预计算 pattern，7B / 8B 全有，70B 未发布。

| 指标 | MHA | GQA |
|---|---|---|
| KV cache 显存降低 | 2.55× | 1.67× |
| decode 提速 | 2.18× | 1.50× |
| pre-filling 提速 | 1.73× | 1.63× |
| pre-filling 显存降低 | 2.38× | 1.53× |

**代价**：短上下文几乎无收益（streaming 头仍保留约 80 个 sink+recent token）；retrieval 头的计算与显存一点不降；retrieval 比例与 τ 是模型相关超参。

> **三个坑**：① **Mistral-7B-v0.3 的 pattern 文件有误**（只有 32 层而模型实为 36 层，issue #23），别用那一个；② **`transformers` 必须锁 4.45.2**（issue #18，否则报 `cache_position` 相关错误）；③ 推理侧用标准 `flash-attn==2.6.3` + FlashInfer。
>
> 一个便于迁移的性质：标定产出的 gate 值与 GPU 型号无关（是模型权重的属性），所以在 8×A800 上标定的结果可直接用于单卡 A800 / 4090。

## 五、量化：KIVI

**出处**：ICML 2024，arXiv:2402.02750v2 | **开源**：`jy-yuan/KIVI` | **平台**：单卡 A100 80GB

**问题**：权重量化是**离线优化式**（如 GPTQ 用二阶信息提前算好）；KV cache 是**流式**的，每步生成即新增，必须立刻量化，优化式的开销不可接受，只能退化成 round-to-nearest。而在这种约束下 per-tensor 全量化会失效：key 有少数**固定通道**幅值极大，统一的 scale 被这些离群通道拉爆，正常通道被压扁。

由此两条观察，也就是全文核心的**不对称设计**：

- key 的离群值集中在固定 channel 上 → **key 按 channel 量化**（组大小 G=32）；
- value 没有离群模式 → **value 按 token 量化**（借注意力稀疏性，把误差锁在单个 token 内部）。

**为兼容流式的拆分**：per-channel 量化跨 token 无法流式，因此把 KV 拆成两部分——**分组部分**（每 32 个 token 一组量化存储）+ **残差部分**（最近 128 个 token 保留全精度滑窗）。

**关键数字**：key 沿 channel 分组后注意力相对误差 **47.0 → 9.6**（降约 5×）；value per-token 相对误差 3.55 对 per-channel 49.89；Llama-2-7B 在 CoQA 上 2bit 63.05 对 63.88；**峰值显存降 2.6×（含权重）**；吞吐 2.35~3.47×。

**代价**：**Falcon-7B（MQA，单 KV 头）2bit 掉点大，须用 4bit**；难推理任务（GSM8K）去掉全精度滑窗就崩（伪量化仅 5.76）；残差全精度部分带来额外显存与实现复杂度。

> 2.6× 是**峰值显存降低且含权重**，不是纯 KV cache 的降低比例——单看 KV 的降低幅度比这个数字大。
>
> 用 GQA 模型（Llama-3 系、Qwen2.5 等）做实验时，2bit 未必可行，需先自行验证；MQA 上论文已明确失效。这一条直接关系到本课题：目标模型 Qwen2.5-7B 就是 GQA。

## 六、卸载：ShadowKV

**出处**：arXiv:2410.21465v3 | **开源**：`ByteDance-Seed/ShadowKV` | **平台**：单卡 A100 80GB，上下文至 1M

**核心分工**：发现 **pre-RoPE 的 key 是极低秩的**，可以只存它的低秩投影；而 **value 不是低秩的**，所以卸载到 CPU，配合在线重建。

**方法**：

1. pre-RoPE key 只存低秩投影（rank=160）；value 卸载到 CPU，用时在线重建。
2. 卸载后取数慢，用**多流重叠**把 value 取数与 key 低秩重建重叠，掩盖 PCIe 传输。
3. post-RoPE 的 key 有局部性 → 分块取均值作 landmark 选重要块；另把 **0.2%~0.3% 的难近似 outlier 块**存为 GPU 上的静态高精度缓存，补精度。
4. 三者配合：key 低秩省显存 → value 卸载省显存 → 少量 outlier 补精度。

**关键数字**：KV 显存理论上限降 **7.08×**，实测 **6× 压缩不掉精度**；取数开销降 2×；无精度损失下支持 6× 更大 batch，吞吐最高 **3.04×**。

**代价**：论文**没有独立的 Limitations 章节**。隐含代价：① 逐 token 经 PCIe 拉取 value，靠重叠掩盖；② **CPU 内存必须装得下完整 value cache**，长序列 × 大 batch 时可达数十 GB；③ 收益随 KV head 数减少而下降；④ 结论全部基于 A100，**未测消费级卡**。

> **口径**：3.6× A100 是"**等效带宽**"，不是端到端吞吐；端到端吞吐是 3.04×。
>
> 它的可行性前提是 CPU 内存足够装完整 value cache——报"显存降 6×"时必须同时报这个前提，否则越界只是从 GPU 挪到了 host。

## 七、横向对比：三个口径不能互换

| 论文 | 压缩或节省 | 吞吐或速度 | 精度 |
|---|---|---|---|
| PagedAttention | 显存利用率 20~38% → 近 100% | 吞吐 2~4×，并发请求数 30.42 | 无损失 |
| H2O | KV 5× 压缩 | 吞吐至多 29×（对 CPU offload 基线） | 20% 预算持平 |
| SnapKV | 92%（1024）/ 68%（4096）压缩 | 生成加速 3.6×，内存效率 8.2× | 几乎无损 |
| Scissorhands | 最多 5× | **未给 wall-clock** | 15~30% 保留仍保持 |
| KIVI | 显存 2.6×（含权重） | 吞吐 2.35~3.47× | 2bit 近乎无损（除 MQA） |
| ShadowKV | 6× 压缩（上限 7.08×） | 吞吐 3.04×（等效带宽 3.6×） | 不掉 |
| DuoAttention | KV 显存 2.55×（MHA）/ 1.67×（GQA） | decode 2.18× / 1.50× | 近无损 |
| Ada-KV | 4×（GQA 兼容带来的进一步减少） | 与 SnapKV 持平 | 同预算下更好 |

**压缩比（显存 / 容量）、吞吐提升、单请求延迟下降，是三个不同的量，不能互换。** 这张表里只有 Scissorhands 一项没有任何时间侧数据，偏偏它的 5× 最常被误读成"加速 5×"。

## 八、这批方法共同的边界：长上下文

**除 PagedAttention 外，全部方法的收益都出现在长上下文场景。**

原因可以直接从第一篇那张 KV 占比表读出来：短上下文、小 batch 时 KV 读取只占每步访存的 4%~9.5%，即使把 KV 全部压掉，天花板也只有个位数百分比。而长上下文 + 大 batch 时 KV 占比到达 65%，此时压缩才有意义。

这条边界在选方法时比"选哪篇论文"更靠前。对本课题的实际含义：

| 若做长上下文（超过 16K） | 若做短上下文（低于 1K） |
|---|---|
| 主线是 KV 压缩，复现对象 KIVI 或 SnapKV | 主线是权重量化（下一篇），KV 压缩收益上限个位数 |
| 4090 的 24GB 是最紧约束 | 4090 上也能跑，重点在 4090 |
| 与投机解码组合的意义小 | 与投机解码组合更有意义（都是单请求低并发） |

按 A800 实测的判据，第二步应该是先扫出 4090 上"显存逼近 24GB 的那一档上下文"，边界落在 8K 以下就转短上下文路线。这个边界不能靠公式估——vLLM 有 `gpu_memory_utilization` 预留、有 KV 分块、有 prefix caching，实际占用和理论值差得不小。

## 九、小结

1. 五类解法省的东西完全不同：浪费、内容、头、位宽、位置。可以叠用，但不可互换口径。
2. 驱逐 / 稀疏一路的演进链最清楚：H2O → SnapKV（补 prompt 侧）→ Ada-KV（补每头预算）。
3. DuoAttention 是这批里少数能改善 prefill 的方法；ShadowKV 也能，代价是 CPU 内存。
4. 除 PagedAttention 外，全部方法收益都在长上下文。短上下文场景下 KV 压缩的天花板只有个位数百分比。
5. 引用纪律：加速比必须带基线与平台。H2O 的 29× 是对 CPU offload 基线、GPTQ 式的多卡换算不算算法加速、Scissorhands 没有 wall-clock 数字。
