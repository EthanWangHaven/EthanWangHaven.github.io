毕设方向定了之后，我和师兄讨论的第一个问题不是"用哪个加速方法"，而是更前面的：推理时间到底花在哪。这个问题不量化清楚，后面所有的"加速"都无从谈起——不知道时间在哪，也就不知道收益该出现在哪。

这篇笔记把我读的第一批文献（6 篇，以实测和建模为主）的归因结论，和我在 A800 上亲手跑的几组数字放在一起。系列里后面几篇的 KV Cache、投机解码、权重量化，都能从这篇的结论里找到自己的位置。

## 先把账算清楚：decode 占了 95% 以上

LLM 推理分两个阶段，行为完全不同。prefill 一次前向吃下整条 prompt，所有 token 并行算，矩阵乘的 m 维很大，是计算密集型的活；decode 每次前向只吐一个 token，矩阵乘退化成矩阵-向量乘（GEMV），是访存密集型的活。

Mind the Memory Gap（arXiv:2503.08311）在 H100 上用 Nsight 逐 kernel 实测，两个阶段的时间占比（表 I，两列之和恒为 1.00）：

| 模型 | prefill | decode |
|---|---|---|
| OPT-1.3B | 0.03 | 0.97 |
| OPT-2.7B | 0.05 | 0.95 |
| Llama-2-7B / 13B | 0.05 | 0.95 |

Cross-Layer 那篇在 A100 80GB 上给了同一量级的数字（0.95~0.97），可以交叉印证。也就是说，优化的全部重心在 decode，prefill 基本不用管。

不过这个 95% 我第一次看到差点直接抄进开题报告。后来翻了论文配套的 vLLM fork 才发现，占比是在 offline 模式下测的——profiler 强制所有请求先跑完 prefill、再统一进 decode，不是真实服务里交错执行的比例，而论文正文没披露这件事（是从仓库 README 里读出来的）。所以它是表征性数字，不是任何具体服务的 profile 结果，引用时得带这个限定。

## 瓶颈不在算力，在显存带宽

decode 为什么慢？看它每步干什么：把整个模型的权重从显存（HBM）搬进片上缓存，跟一个 token 做乘加，产出一个结果。读的数据量是固定的，产出是 1 个 token——这笔买卖怎么算都不划算。

用 roofline 的语言说，decode 阶段的算术强度（每读 1 字节能做多少次运算）极低。LLM Inference Unveiled 给的范围是：

$$
\text{AI}_{\text{decode}} \in [0.25,\ 1.75]\ \text{OPs/byte}
$$

而两张目标卡的转折点（算力峰值 ÷ 带宽峰值）在这：

| 卡 | 架构 | 显存 | 带宽 | 转折点 |
|---|---|---|---|---|
| A800 80GB | Ampere sm80 | 80 GB | 约 2.04 TB/s | 约 153 OPs/byte |
| RTX 4090 | Ada sm89 | 24 GB | 约 1.008 TB/s | 约 164 OPs/byte |

差了两个数量级。同样一份数据搬进来，算力只用了百分之几就已经等不到下一批数据——decode 被显存带宽卡住，跟 SM 没关系。

Mind the Memory Gap 的实测正好是这件事的直接证据：decode 阶段 DRAM 读带宽均值 48%~77%、峰值 93%~99%，带宽真的打满了；写带宽只有 1.82%~5.56%；而算力利用率 decode 大部分时间不到 20%，全程实测算力只到峰值的 3.5%~3.8%（这个百分比是论文只给绝对值、我拿数字回算的）。一边 99%，一边不到 4%，这就是所谓的访存墙。

顺带一提，这篇论文自己的数字也经不起细抠。表 II 里 25.6 TFLOP/s 的"算力峰值"是仓库出图脚本把 Nsight 的 ffma / dfma 指标弄反取到的 FP64 峰值，比 H100 PCIe 真实 FP32 峰值（51.2 TFLOPS）低了约一倍，所以"离 roofline 差几个数量级"这句话实际上被放大了。定性结论不受影响，但抄数字之前得挑一挑——我后来养成了习惯，凡是要引的数字都回表格里核一遍。

## 三条瓶颈，三个方向

把上面的结论再拆一层，可以归成三条互相独立的瓶颈：

```
① 权重读取      每步都要把全部权重读一遍（7B bf16 约 15 GB）
② KV Cache 搬运  每步都要把整条 KV cache 读一遍，随长度 × batch 线性涨
③ 自回归串行     读了这么多数据，只出一个 token
```

三条各自长出了一个方向的解法：① 压权重位宽（权重量化），② 让 KV 变小或少读（KV 压缩），③ 一次前向多验证几个 token（投机解码）。②和③是正交的——一个动"每次读多少字节"，一个动"每次读产出多少 token"；①和②也正交，一个压权重侧一个压缓存侧。

但正交只说明可以叠用，不代表收益能相加。第三篇里有个具体的反例，先按下不表。

## 我在 A800 上测的几组数字

文献里全是 A100 / H100 / V100，我的两张卡（A800、4090）一个实测数字都没有——这是 22 篇读完之后最直接的空白，也是我动手跑 baseline 的理由。哪怕只有三行自己的数字，也比引用十篇论文的图硬。

平台：单卡 A800 80GB PCIe 独占，vLLM 0.19.0，torch 2.10.0+cu128，Qwen2.5-7B bf16，`temperature=0`。

### batch 扫描：拐点在 batch 8 之后

输入 96 token（各请求互不相同，关前缀缓存）、输出 512 token，扫 batch：

| batch | 输出 tok/s | 单请求 tok/s | 相对上档 |
|---:|---:|---:|---:|
| 1 | 94.8 | 94.8 | — |
| 2 | 190.2 | 95.1 | 2.01× |
| 4 | 383.8 | 96.0 | 2.02× |
| 8 | 738.0 | 92.2 | 1.92× |
| 16 | 1,422.8 | 88.9 | 1.93× |
| 32 | 2,638.0 | 82.4 | 1.85× |
| 64 | 4,351.4 | 68.0 | 1.65× |

1 到 8 几乎完美线性，说明这一段带宽没吃满、加 batch 就是白捡；16 之后开始衰减，32 到 64 只剩 1.65×，同时单请求速度从 94.8 掉到 68.0（掉了 28%）。这跟 Mind the Memory Gap 在 H100 上的定性结论对得上：batch 变大并不会把瓶颈从访存挪到算力，只是让带宽逐步贴近饱和。

### 上下文扫描：涨 32 倍，只掉 13%

单请求、输入从 1K 扫到 32K、输出 128 token：

| 输入 token | 输出 tok/s | 相对 1K |
|---:|---:|---:|
| 990 | 92.3 | 100% |
| 4,095 | 91.9 | 99.6% |
| 8,190 | 89.6 | 97.1% |
| 16,380 | 85.3 | 92.4% |
| 31,995 | 80.3 | 87.0% |

roofline 在最右那档预测 82.4，实测 80.3，误差 2.6%。这个误差小到我有点意外——roofline 在 decode 上比我想象的管用，后面拿它做预筛工具是靠谱的，不是只能画在 slides 里讲故事。

### 决定性的量：KV 读取占比

把 batch 固定 32，只改上下文长度，把每步读取量拆成权重和 KV 两部分：

| 上下文 | KV 读取 | 权重读取 | KV 占比 | 解码 tok/s | 相对最短 |
|---:|---:|---:|---:|---:|---:|
| 96 | 0.63 GB | 15.3 GB | 4% | 2,638 | 100% |
| 900 | 1.6 GB | 15.3 GB | 9.5% | 2,568 | 97.4% |
| 15,975 | 28.6 GB | 15.3 GB | 65% | 1,211 | 45.9% |

KV 占比从 4% 到 65%，解码吞吐掉了 54%。这张表是我这轮实验里最值钱的一张，它给出一维判据：KV 占比低于 10% 时权重主导，该做权重量化，KV 压缩的天花板只有个位数百分比；高于 65% 时 KV 主导，压缩空间最大；中间那段两者都重要，得实测交叉点，文献里没有这个区间的数据。

单独看 batch 或单独看上下文都会误判——决定性的是两者的乘积带来的 KV 读取占比。

### prefill 侧：一个被推翻的预测

关掉前缀缓存，16K 输入扫 batch，prefill 稳定在 10,000 tok/s 左右，对应 7B 模型约 45% 的算力利用率——跟 decode 不到 4% 放在一起，"prefill 计算受限、decode 访存受限"这句话就有了自己的数字。

原本我预计 batch 64 会撞上 KV 容量上限（1,022,400 对 1,021,536，就差那么一点）出现性能断崖，实测只比线性外推慢 5%：

```
48 ÷ 32 = 1.500   → 实测 1.499  完全线性
64 ÷ 48 = 1.333   → 实测 1.401  慢 5%
```

原因是 chunked prefill（每块 16,384 token）会把超出的块排队，不会崩。文献里"显存越界 → 重算 → 断崖"的说法（Cross-Layer 在 A100 上观测到 93.2 秒的延迟尖峰）是在不开分块预填的配置下测的，两边并不矛盾——但"显存越界即断崖"这句话，至少在 chunked prefill 下不能直接写进报告。

### 一个方法学的坑：前缀缓存

这轮实验里最值得记的教训。最初我用同一段 prompt 复制 32 份做 batch 扫描，wall time 只有 6.8 秒，数字好看得可疑；把 prompt 改成互不相同、关掉前缀缓存之后，同配置变成 51.1 秒，差 7.5 倍。原因是 vLLM 默认开 prefix caching，相同 prompt 的 prefill 被整个去重了——我测出来的"吞吐"里根本没有 prefill。

所以现在我每个吞吐数字都同时报四件事：prompt 是否互异、前缀缓存开关、输入输出长度、测的是 prefill 还是 decode。缺一项就没法复现。可重复性方面，同配置跑三次，差异都在 0.5% 以内。

## 小结

三条结论：decode 占 95% 以上，所以优化都在 decode；decode 的算术强度比两张卡的转折点低两个数量级，属于硬性访存受限；瓶颈可拆成权重读取、KV 搬运、自回归串行三条，后面三篇各对应一条。外加一条自己的：KV 占比是选方法的起点，4% 到 65% 之间吞吐差了 54%。
