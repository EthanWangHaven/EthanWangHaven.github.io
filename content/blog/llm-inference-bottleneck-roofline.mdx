这一篇是本科毕设「面向自动驾驶模型的推理加速与部署优化」的第一篇笔记。做推理加速最先要回答的不是"用哪个方法"，而是"时间到底花在哪"。把这件事量化清楚之后，后面几篇讲的 KV Cache 压缩、投机解码、权重量化，各自能解释一部分、也各自有失效区间。

记录顺序：先给文献里的归因结论，再给在 A800 上自己跑出来的三组扫描，最后把两条合起来，得到一个"该用哪类方法"的判据。



## 一、基本事实：decode 占了 95% 以上的时间

LLM 推理分两个阶段，行为完全不同：

- **prefill（预填充）**：一次前向处理整条 prompt，所有 token 并行，矩阵乘的 m 维很大，属于计算密集。
- **decode（解码）**：每次前向只产出一个 token，矩阵乘退化成矩阵向量乘（GEMV），属于访存密集。

*Mind the Memory Gap*（arXiv:2503.08311）在 H100 上用 Nsight 实测，给出了 prefill / decode 两个阶段占总推理时间的归一化份额（表 I，两列之和恒为 1.00）：

| 模型 | prefill | decode |
|---|---|---|
| OPT-1.3B | 0.03 | **0.97** |
| OPT-2.7B | 0.05 | **0.95** |
| Llama-2-7B | 0.05 | **0.95** |
| Llama-2-13B | 0.05 | **0.95** |

同一篇论文的图 4 显示，prefill 即使在大 batch 下也低于 5%。

> **提醒**：这个占比是在 offline 模式下测的，profiler 强制所有请求先跑完 prefill 再统一进入 decode，不是真实 serving 下交错执行的比例。论文正文未披露这一点，是从仓库 README 里读出来的。所以"decode 占 95%"是一个表征性数字，不是任何具体服务的 profile 结果。

另有一篇 *Cross-Layer Performance Analysis of Single-GPU LLM Inference* 在 A100 80GB 上给出同一量级的结论（0.95~0.97），可作交叉印证。

**优化的全部重心因此落在 decode 上。**

## 二、瓶颈不在算力，在显存带宽

decode 为什么慢，要看它每一步做了什么：把模型全部权重从显存（HBM）读进片上缓存（SRAM），和一个 token 做一次乘加，然后只产出一个结果。读的数据量是固定的，产出的 token 是 1 个。

用 roofline 模型的语言：decode 阶段的算术强度（arithmetic intensity，每读 1 字节能做多少次运算）极低。*LLM Inference Unveiled* 给出的范围是：

$$
\text{AI}_{\text{decode}} \in [0.25,\ 1.75]\ \text{OPs/byte}
$$

而两张目标卡的转折点（算力峰值 ÷ 带宽峰值）分别是：

| 卡 | 架构 | 显存 | 带宽 | 算力 | 转折点 |
|---|---|---|---|---|---|
| A800 80GB | Ampere sm80 | 80 GB | 约 2.04 TB/s | 约 312 TFLOPS（FP16 张量核） | 约 **153** OPs/byte |
| RTX 4090 | Ada sm89 | 24 GB | 约 1.008 TB/s | 约 165 TFLOPS | 约 **164** OPs/byte |

算术强度比转折点低了**两个数量级**。这意味着同样一份数据搬进来，算力只用了百分之几就已等不到下一批数据——整个 decode 阶段被显存带宽卡住，不是被 SM 卡住。

*Mind the Memory Gap* 的实测数字正是这一点的直接证据（H100，xFormers 后端）：

- decode 阶段 DRAM **读**带宽均值 **47.98%~76.75%**，**峰值 93%~99%**——带宽确实被打满了；
- 而**写**带宽只有 **1.82%~5.56%**；
- Compute Warps in Flight 均值无模型超过 **35%**，decode 阶段低至 **9.85%~31.14%**；
- 实测算力只到 roofline 算力峰值的 **3.5%~3.8%**（该百分比由绝对值回算）。

一边是带宽 93%~99%、一边是算力不到 4%。这就是"访存墙"（memory wall）。

> **提醒两处口径**：这篇论文表 II 的算力峰值 25.6 TFLOP/s 是仓库出图脚本把 `ffma` / `dfma` 弄反取到的 **FP64 峰值**，比 H100 PCIe 的真实 FP32 峰值（51.2 TFLOPS）低约 2 倍，所以"离 roofline 差几个数量级"这个说法被放大了；文中的访存峰值 1.63 TB/s 是 Nsight 的"可达峰值 DRAM 带宽"，也不是 datasheet 的 3.35 TB/s。定性结论不受影响，绝对数字引用前要挑。

## 三、三条瓶颈，三代解法

把上面的结论再往下拆一层，可以归为三条互相独立的瓶颈，后面三篇各对应其中一条：

```
瓶颈 ①  权重读取            每步都要把全部权重读一遍（7B 模型 bf16 约 15 GB）
         └→ 对策：压权重位宽（量化）           → 第四篇

瓶颈 ②  KV Cache 搬运        每步都要把整条 KV cache 读一遍，随长度 × batch 线性增长
         └→ 对策：让 KV 变小 / 少读             → 第二篇

瓶颈 ③  自回归串行           读了这么多数据，只出一个 token
         └→ 对策：一次前向多验证几个 token      → 第三篇
```

三条对应三种思想轴：

| 瓶颈 | 思想轴 | 代表方法 | 是否无损 |
|---|---|---|---|
| ① 权重读取 | 每次少读一点（位宽） | AWQ、GPTQ、SmoothQuant | 近无损（4bit 有轻微掉点） |
| ② KV 搬运 | 每次少读一点（内容 / 位置 / 位宽） | PagedAttention、H2O、SnapKV、KIVI、ShadowKV | 驱逐类不可逆，其余近无损 |
| ③ 串行解码 | 一次读取多产出几个 token | Medusa、EAGLE、Lookahead | 拒绝采样下无损 |

② 和 ③ 是正交的：一个动"每次读多少字节"，一个动"每次读产出多少 token"。① 和 ② 也正交：一个压权重侧，一个压缓存侧。

但"正交"只说明可以叠用，**不代表收益可以相加**。第三篇会看到具体的反例。

## 四、在 A800 上自己测的一组数字

上面全是文献里 A100 / H100 的结论。两张目标卡（A800、RTX 4090）在这批文献里没有任何实测数据——这是读完全部 22 篇之后最直接的空白。所以第一步是把 baseline 跑出来。

平台与配置：**单卡 A800 80GB PCIe 独占**、vLLM 0.19.0、torch 2.10.0+cu128、Qwen2.5-7B（bf16）、`temperature=0`、`ignore_eos=True`。

### 4.1 解码吞吐随 batch 的变化

输入 96 token（各请求互不相同，关前缀缓存）、输出 512 token，扫 batch：

| batch | 耗时 s | 输出 tok/s | 单请求 tok/s | 相对上档 | 峰值显存 GiB |
|---:|---:|---:|---:|---:|---:|
| 1 | 5.40 | 94.8 | 94.8 | — | 74.7 |
| 2 | 5.38 | 190.2 | 95.1 | 2.01× | 74.7 |
| 4 | 5.34 | 383.8 | 96.0 | 2.02× | 74.7 |
| 8 | 5.55 | 738.0 | 92.2 | 1.92× | 74.7 |
| 16 | 5.76 | 1,422.8 | 88.9 | 1.93× | 74.7 |
| 32 | 6.21 | 2,638.0 | 82.4 | 1.85× | 74.7 |
| 64 | 7.53 | **4,351.4** | 68.0 | **1.65×** | 74.7 |

**拐点在 batch 8 之后。** 1→8 几乎完美线性（每档 1.92~2.02×），说明这一段仍然是"带宽没吃满、加 batch 就是白捡"；16 之后开始衰减，32→64 只剩 1.65×。与此同时单请求速度从 94.8 掉到 68.0（−28%）。

这一条与 *Mind the Memory Gap* 在 H100 上的定性结论一致：batch 变大不会把瓶颈从访存挪到算力，只是让带宽逐步贴近饱和。

### 4.2 上下文长度的影响

单请求、输入从 1K 扫到 32K、输出 128 token：

| 输入 token | 输出 tok/s | 相对 1K |
|---:|---:|---:|
| 990 | 92.3 | 100% |
| 4,095 | 91.9 | 99.6% |
| 8,190 | 89.6 | 97.1% |
| 16,380 | 85.3 | 92.4% |
| 31,995 | 80.3 | 87.0% |

上下文涨了 32 倍，速度只掉 13%。roofline 模型在这一档预测 82.4，实测 80.3，**误差 2.6%**——说明 roofline 对 decode 阶段是有效的预测工具，不是只能讲故事。

### 4.3 核心：KV 占比决定解码吞吐

把 batch 固定为 32，只改上下文长度，把每一步的读取量拆成"权重"和"KV cache"两部分：

| 上下文 | KV 读取 | 权重读取 | **KV 占比** | 解码 tok/s | 相对最短 |
|---:|---:|---:|---:|---:|---:|
| 96 | 0.63 GB | 15.3 GB | **4%** | 2,638 | 100% |
| 900 | 1.6 GB | 15.3 GB | **9.5%** | 2,568 | 97.4% |
| 15,975 | 28.6 GB | 15.3 GB | **65%** | 1,211 | **45.9%** |

**KV 占比从 4% 升到 65%，解码吞吐掉了 54%。**

这张表是后面所有方法选择的依据。它给出的是**一维判据**：

| KV 读取占比 | 主导项 | 该做什么 |
|---|---|---|
| < 10%（短上下文、小 batch） | 权重 | 权重量化；KV 压缩的天花板只有个位数百分比 |
| 10%~60% | 两者都重要 | 需要实测交叉点，文献里没有这个区间的数据 |
| > 65%（长上下文、大 batch） | KV | KV 压缩 / 驱逐，空间最大 |

单独看 batch 或单独看上下文都会误判——决定性的量是两者的乘积带来的 KV 读取量占比。

### 4.4 prefill 这一侧

关掉前缀缓存，16K 输入、输出 256，扫 batch：

| batch | prefill token 总量 | 耗时 s | prefill tok/s |
|---:|---:|---:|---:|
| 32 | 511,200 | 51.1 | 10,004 |
| 48 | 766,800 | 76.6 | 10,011 |
| 64 | 1,022,400 | 107.3 | 9,529 |

prefill 稳定在约 **10,000 tok/s**，对应 7B 模型约 45% 的算力利用率——与 decode 阶段不到 4% 的算力利用率形成鲜明对比。这正是"prefill 计算受限、decode 访存受限"的直接验证。

原本预计 batch 64 会因为 KV 容量越界（1,022,400 > 1,021,536）出现性能断崖，实测只比线性外推慢 5%：

```
48 ÷ 32 = 1.500   → 实测 1.499  完全线性
64 ÷ 48 = 1.333   → 实测 1.401  慢 5%
```

原因是 **chunked prefill**（每块 16,384 token）会把后续块排队，不会崩溃。**"显存越界即断崖"在分块预填下不成立**，这条与 *Cross-Layer* 在 A100 上观测到的"越界 → 重算 → 延迟尖峰 93.2 秒"并不矛盾：那边跑的是不启用 chunked prefill 的配置。

## 五、一个必须交代的方法学坑：前缀缓存

上面 D 组的数字之所以可信，是因为每个请求的 prompt 互不相同，且关掉了前缀缓存。

一开始用同一段 prompt 重复 32 次做 batch 扫描时，拿到的是"wall time 6.8 s"这样的数字；把前缀缓存关掉、prompt 改成互不相同之后，同配置的 wall time 变成 51.1 s，**相差 7.5 倍**。

原因是 vLLM 默认开启 prefix caching，相同的 prompt 已经被去重，wall time 里只剩解码部分，prefill 完全没被测到。

**结论**：任何 throughput 数字都必须同时报告四项——prompt 是否互异、前缀缓存是否开启、输入输出长度、测到的是 prefill 还是 decode。缺一项，数字就无法复现。这条要求后面每一篇都会照做。

可重复性方面，同一配置重复三次，全部结果差异在 0.5% 以内。

## 六、小结

1. decode 占推理总时间 95% 以上，prefill 不到 5%。
2. decode 的每个算子算术强度只有 0.25~1.75 OPs/byte，比 A800 / 4090 的转折点低两个数量级，属于硬性访存受限。
3. 瓶颈可拆成三条：权重读取、KV cache 搬运、自回归串行。后面三篇依次对应。
4. A800 实测：batch 8 之后吞吐增益衰减，上下文涨 32 倍速度只掉 13%，而 **KV 占比从 4% 升到 65% 时解码吞吐掉 46%**——这条一维判据是选方法的起点。
5. 报吞吐必须带四项口径，否则不可复现。
