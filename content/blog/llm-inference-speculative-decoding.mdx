前两篇处理的是"每次读多少数据"——KV cache 和权重位宽。这篇换一条轴：每次读完能产出多少 token。

瓶颈在这里：decode 每步把整个模型权重读一遍，只产出一个 token。权重读取量是固定的、没法"少读"，唯一的出路是让这次读取多干点活。投机解码干的就是这件事。

## 这笔账怎么算

投机解码的基本框架叫 draft-then-verify：每步先用一个便宜的草稿器猜出若干个未来 token，再让目标模型一次前向并行验证这批候选，接受最长的正确前缀。

```
常规解码    前向 → 1 token，前向 → 1 token，前向 → 1 token   （3 次前向 = 3 token）
投机解码    草稿出若干候选 → 目标模型一次前向验证 → 接受 k 个  （1 次前向 = k+1 token）
```

每步省下 k 次目标模型前向，多付一次草稿开销加一次验证开销，加速比就是这笔账的比值。k（接受长度）取决于草稿器的准确率——所以整条技术路线的进化史，本质上就是"怎么让草稿又便宜又准"的历史。

走投机采样判据时，输出分布与目标模型严格一致。核心公式（Leviathan 等 2023）：对草稿 token 以 $\min(1, p(x)/q(x))$ 的概率接受；一旦拒绝，就在残差分布 $p'(x) = \max(0, p(x)-q(x)) / \sum_x \max(0, p(x)-q(x))$ 上重新采样。可以证明这样采出来的 token 服从 p。

但"无损"两个字我写开题时反复掂量过，有三处限定，不能笼统写成"输出分布完全一致"。FP32 下才严格成立，投机解码综述 §D.3 明写 FP16 下浮点误差会累积，而它自己的实测全部是 FP16——理论与实践在这里有一道缝。Medusa 的 typical acceptance 论文自陈偏离了"输出精确对应原模型分布"，拿一致性换加速率，只有走拒绝采样才保持。Lookahead 的分布保持证明有前提（采样验证算法 + 生成端强制贪心），它的贪心路径在 FP16 下与 HuggingFace greedy search 并不逐字一致。

## Medusa：把解码头焊在主干上

独立 draft 模型这条路的问题是：草稿模型既要够小又要够准，往往得单独预训练——Medusa 转引的数字是 275 个 A100 GPU 小时。而且独立预训练会带来 draft 和 target 之间的分布偏移，target 会拒绝 draft 的续写。

Medusa（ICML 2024）干脆取消 draft model：在主干最后一层隐状态上挂 K 个轻量解码头，第 k 个头预测未来第 k+1 个位置的 token：

$$
p_t^{(k)} = \text{softmax}\left(W_2^{(k)} \cdot \text{SiLU}(W_1^{(k)} h_t) + h_t\right), \quad
W_2^{(k)} \in \mathbb{R}^{d \times V},\ W_1^{(k)} \in \mathbb{R}^{d \times d}
$$

再用 tree attention 一次前向验证整棵候选树。因为头长在主干的表示之上，分布偏移问题顺手就消掉了。

训练分两档，数字必须分开报：MEDUSA-1 冻结主干只训头，7B 上 2.18×、13B 上 2.33×；MEDUSA-2 联合微调主干，7B / 13B 都到 2.83×，但要配组合损失、差分学习率（头取主干的 4 倍）、头部预热三件套。消融分解很清楚：只加头约 1.5×，加 tree attention 约 1.9×，优化树配置约 2.2×，联合微调约 2.8×。

两个口径容易踩。所有加速比都是 batch size 1 的 wall-time、相对默认 HuggingFace 实现；附录 G 里那个"44× FLOP/s"是单个算子在 roofline 上的提升，当成端到端加速比引用就是量级错误。树也不是越大越好：64 节点的稀疏树比 256 节点的稠密树还好，加速率按对数增长，树太大反而慢，因为线性层和注意力矩阵乘的开销把这一步推进了计算受限区。

## EAGLE：草稿搬到特征层

7B 这一档没有现成的草稿模型：同系列没有更小的，拿 7B 当 13B 的草稿自己开销就太大——EAGLE 实测过，13B 上没有任何加速，33B 只有 1.12×。EAGLE 的做法是草稿不在 token 层做，搬到特征层。理由是 token 序列只是自然语言的简单变换，特征序列更规整；但特征是高维连续量，下一个特征取决于采样结果，于是把"提前一个时间步"的 token 作为已知条件喂进去。单变量消融的路径：token 层 1.5× → 特征层 1.9× → 加提前 token 2.8×。

结构上很省：只训一个 transformer decoder 层（7B 对应 0.24B 参数），Embedding 和 LM Head 直接复用 target 的、不参与训练。训练用 Smooth L1 加一路分类损失（权重 0.1，因为分类损失数值上大一个数量级），特征上加 $U(-0.1, 0.1)$ 噪声防误差累积。

MT-bench 上整体 2.1×~3.8×，代码生成最好（HumanEval 3.76×）——代码固定模板多，草稿好出。要留意两点。一是它的理论支点"特征层不确定性低于 token 层"其实缺直接证据：论文给的是概念论述加一组单变量消融，没有熵或方差的测量，引用时写"论文以消融支持"比较稳。二是草稿权重常驻显存：Vicuna 7B 在 24GB 的 3090 上最大 batch 从 8 挤到 7。这对 24GB 的 4090 是硬约束，论文自己没测过 4090。

顺带记一个后文要用的数字：EAGLE 和 gpt-fast 的 int4 量化联合（3090、LLaMA2-Chat 7B）拿到 160.4 token/s，对比单独 gpt-fast int4 的 106.9——这是"量化 + 投机解码可以叠"的最硬证据。

## EAGLE-2：静态树改动态树

EAGLE-1 的草稿树是静态的，所有上下文共用一套形状。EAGLE-2 发现 EAGLE 的草稿模型校准良好——置信度能小幅误差地逼近接受率，置信度低于 0.05 的草稿 token 接受率约 0.04，高于 0.95 的约 0.98——于是用置信度当接受率的代理，动态改树形：每个节点定义"值"为路径上接受率的连乘（理由是一个 token 被接受的前提是全部前缀都被接受），扩展时取当前层值最高的 top-k，重排时对全部草稿 token 按值取全局 top-m。不改训练、不改验证，六个任务平均加速 4.04×（Vicuna 13B，T=0），比 EAGLE-1 快 20%~40%。

一个容易读错的点："动态"不等于按上下文长度伸缩。动态指的是同一上下文内按节点值选择性扩展，树深度和草稿 token 上限仍是逐模型规模手工设的常数。另外论文没印 GPU 型号也没报显存占用，接 4090 之前得自己先测显存。

## 两个极端：LayerSkip 和 Lookahead

LayerSkip 是八篇里唯一不额外占显存的，出发点是个有点丧的测量：Llama1 7B 平均一个 token 要用到 23.45 / 32 层，就算有个零开销的完美预测器也只能省 26% 的计算。结论：不能只改推理挑层，得改训练，让模型少依赖后层。配方是层丢弃（前层低丢率、后层高丢率）加早退损失（低层直接接共享 LM head），推理时前 E 层自回归出草稿、后 L−E 层一次前向验证，KV cache 只维护一份。

代价全压在训练侧：得自己微调一份权重，超参一堆（丢率、早退权重、课程类型）。而且收益完全由早退层精度决定——早退单跑质量崩得厉害，CNN/DM 的 ROUGE-2 从 0.079 掉到 0.012，全靠自验证拉回来。加速比 1.34×~2.16×。摘要里的三个头条数各来自不同训练配置和不同卡（2.16× 是从头预训练 + CNN/DM + H100，1.82× 是代码微调 + A100，2.0× 是任务微调 + H100），不能合成一句"三种任务都约 2×"。论文自己还有前后不一致：摘要说最高 2.16×，结论节说最高 1.86×，引用以表格为准。

Lookahead 在另一个极端：完全免训练，雅可比迭代加 n-gram 池，候选直接从历史里检索。常被引的 4× 是 8 卡强扩展口径，不是单卡端到端数字；n-gram 池的显存论文只说了句 "huge memory"，没给实测值。

## 正交，但不相加

三条轴（KV、权重、token 数）理论上可以叠。EAGLE + gpt-fast 那张表是正例：FP16 下 55.1 → 100.2，int4 下 106.9 → 160.4，两边都涨。Draft & Verify 把量化叠在自己方法之上也是正例（bf16 1.53×、fp8 1.61×）。

但同一张表里有个反例：叠加稀疏化之后，Draft & Verify 自己的相对加速比反而从 1.57× 掉到 1.47×。论文的解释是基座模型本身也被加速了——分母变大，相对收益自然缩水。

所以结论是：可叠加不等于收益相加，组合收益必须实测。这正是我实验清单里排了的一个组合实验——投机解码与 KV 压缩是否真的正交，文献里没有人验证过，因为 EAGLE 的草稿生成依赖 KV cache 的完整性，把 KV 压到 50% 或 2bit 之后草稿准确率很可能下降，吃掉加速比。这个问题的答案只能测出来。

## 共同的死穴

这批方法全部只作用于 decode，prefill 一点不受益——跟 KV 那批正好相反，那边 DuoAttention 和 ShadowKV 都能改善 prefill。

更要命的是 batch 一大收益就消失。投机解码靠的是"批量没用完的闲置算力"，批量把算力吃满，它就没得换了。EAGLE 自己的表：bs 1→4，LLaMA2-Chat 70B 从 3.01× 降到 2.40×。所以它只适合单请求、低并发的延迟敏感场景——恰好是我第一篇里 batch=1 时 94.8 tok/s 的那个场景。反过来，如果我做的是大 batch 吞吐优化，这批方法基本可以划掉。

## 写在最后

按落地成本记这五条路线最实用：Lookahead 免训练但要收 n-gram 池的显存；Medusa 只训头，最简单，且已并入 vLLM / TRT-LLM；EAGLE 按 target 各训一份草稿（0.24B~0.99B），代码最稳；LayerSkip 要自训权重，代价在训练侧；Draft & Verify 免训练但代码链接未核实。

最后一条引用纪律：常被引的"接受率阈值 35%~45%"这个数字，我在一手文献里没有查到出处——它只在二手整理里出现过。要写进报告，得回原论文核对或自测确认，不能直接转引。
